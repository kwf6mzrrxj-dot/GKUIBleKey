# 提交前审查清单（REVIEW_CHECKLIST）

> 这份文件不是审查报告，是**下一次审查要逐项打勾的清单**。
>
> 它的每一条都是从本项目 v4.4–v4.9 六轮审查里**真实踩过的 bug** 反推出来的
> （约 30 个功能缺陷 + 17 项死代码）。写报告的文档已经有 2400+ 行，
> 但那些是"这次发现了什么"；这份是"下次怎么查"。
>
> **用法**：改完代码、编译通过之后，从上到下过一遍，每条回答「是/否/不适用」。
> 任何一条「否」都不算完成。**不要凭记忆，逐条对照本次 diff。**

## 一、最高频两类（占历史缺陷 1/3，优先过）

### A. 静默失败 / 假成功

| # | 检查项 | 反例（真实发生） |
|---|---|---|
| A1 | 每个 `guard … else { return }`，**调用方是否知道它失败了**？ | `beginMeasuredAuth` 在链路未就绪时 `return`，预认证被静默丢弃，之后无人重试 → 点火不了 |
| A2 | 每个 `_ = f()` / 返回值被丢弃的调用，**丢弃是否安全**？ | `_ = measured.handle(bytes)` 丢掉密钥帧解析结果，于是短帧也报「配对成功」 |
| A3 | 「失败路径」是否改写了 UI 状态，还是留着上一条成功文案？ | `saveKeyData` 失败只 append 日志，`case .keyData` 照样 `lastResult = .paired` |
| A4 | 错误分支是 `return` 就完事，还是**复位了链路/状态并给出恢复路径**？ | 订阅失败只 `note(...); return` → `linkState` 卡 `.discovering`、`writeChar` 仍非 nil → 点按钮往未加密链路发帧，永久假死 |
| A5 | 写 Keychain / 文件失败是否被检测？ | `KeyStore.set` 先删后加，`SecItemAdd` 失败只 `NSLog`，调用方全当成功 |

**验证手法**：对每个 `guard`，问「这条 if 成立时，用户看到什么？他下一步怎么办？」
如果答案是"没有提示、也没人重试"，就是 A1。

### B. 状态机收口 / 超时兜底

| # | 检查项 | 反例 |
|---|---|---|
| B1 | 每个 `xxx = true` 的「进行中」标志，**所有出口都复位了吗**？（成功/失败/超时/断连/被覆盖） | `passiveEntrySwitching = true` 后只在「断连」复位；车端不回 04 也不断开 → 开关永久转圈 |
| B2 | 每个「等待中」状态，**有超时吗**？超时后清干净了吗？ | `pendingPreAuth` 挂起后只有 `.ready` 会消费，永远等不到就永远挂着 |
| B3 | 一次性标志，**成功路径上清了吗**（不只是在扫描回调里清）？ | `forceConnectOnce` 只在 `didDiscover` 清零，走「直连已知设备」时残留 → 操作成功后多一次空连接 |
| B4 | 收到响应就 `cancelTimeout` 的地方，**下一个阶段重新起表了吗**？ | 收到 02 就取消超时，回完 03 不再计时 → 04 不来永久悬挂 |
| B5 | 「任务在飞」时来了新请求，**是排队、拒绝，还是互相覆盖**？覆盖后旧状态谁复位？ | `pendingActionAfterConnect` 只能存一个，无感切换被顶掉后没人复位 |

## 二、协议层专项（逆向工程特有）

| # | 检查项 | 反例 |
|---|---|---|
| C1 | `substringWithRange:` 判断位映射时，**`location` 和 `length` 都读了吗**？ | `_isEnginRunning` 是 `{1,2}` 两位 + `strtol(base 2) == 2`，前两次只看 `mov w2,#1` 当成单 bit → 发动机永远显示未启动 |
| C2 | 位序是否确认了 `hexToBinary:` 的方向（MSB 在前 = `bin[7]` 是 bit0）？ | 见 `VehicleStatus.decodeStatusByte` 的表格 |
| C3 | 分包/长度类公式，**是否按反汇编的加法顺序重算过一遍**？ | 包数应为 `ceil((len+4)/mtu)`，写成 `ceil(len/mtu)` → 179B@mtu182 少算一包，帧被截断 |
| C4 | 有没有把「同一信号两种含义」混用？ | `linkState == .idle` 既表示"停止扫描"又被上层当"断连" → 预认证链被自己掐断 |
| C5 | 位映射/偏移的结论，**有没有至少一个真实数据样本对照**（不只是读反汇编）？ | 发动机案例：只有反汇编、没样本，读漏 length 就错了 |
| C6 | 从原 App 推断的行为，是否区分了「反汇编证据」与「行业常识」？ | 「远离闭锁」曾凭常识脑补，原 App 根本没有 |

**硬规则**：C1/C5 任一条没做到，结论标「未验证」，不能写进"已修复"。

## 三、守卫覆盖面（安全相关必查）

| # | 检查项 | 反例 |
|---|---|---|
| D1 | 这个安全开关，**是加在唯一出口上，还是加在某个入口上**？ | `listenOnly` 只拦 `perform`，预认证 `0x0C` / 配对 `0x0D` 不走 `perform` → 用户以为只读，实际在发加密命令 |
| D2 | 同一个操作有几条等价路径？每条都守了吗？ | 控车走 `perform`（支持排队），无感开关 `setPassiveEntry` 却提前 `guard isWriteReady` 直接拒 → 同一个 App 两套行为 |
| D3 | 防爆破/锁定类拦截，**真的拦住了吗**（不只是记录）？ | `lockoutRemaining` 曾只记录不拦截，等于形同虚设 |

**验证手法**：`grep` 所有发送点（`ble.send` / `perform` / `beginMeasuredAuth`），
逐个确认经过守卫。**"唯一出口"是唯一靠得住的做法。**

## 六、验证门槛（必须标注级别）

| 级别 | 含义 | 能宣称什么 |
|---|---|---|
| L0 | 只改了代码，没编译 | 什么都不能宣称 |
| L1 | `swiftc -typecheck` 通过 | "语法/类型没问题" |
| L2 | `xcodebuild` 成功 | "能构建" |
| L3 | 装机 + 启动 + 日志确认初始化 | "能跑起来" |
| L4 | 真车验证目标行为 | **"修好了"** |

**规则：只有 L4 才能写「已修复」。L1–L3 一律写「已改，待实测」。**

历史教训：v4.5/v4.6/v4.7 三轮都在 L2 就宣称修好，
结果 v4.9 才第一次做 L3（手机解锁后 `devicectl launch` 成功）。

## 七、已知的「掩盖链」——修完 A 必须主动查 B

缺陷会互相掩盖：前一个不修，后一个根本观测不到。本项目的已知链条：

```
预认证能发出去（v4.4）
   └→ 才暴露：.idle 把续发链掐断（v4.7）
        └→ 才暴露：回完 03 不计时，04 不来永久挂（v4.7）
             └→ 才暴露：超时不收口无感开关/Siri/配对状态（v4.9）
连接不再空转（v4.4）
   └→ 才暴露：连接阶段无看门狗，卡「正在连接」（v4.7）
        └→ 才暴露：超时后 pendingActionAfterConnect 残留（v4.9）
状态位映射正确（v4.5）
   └→ 才谈得上验证「点火时状态是否刷新」
```

**动作**：每修完一条，问一句「这条通了之后，下一个环节会暴露什么？」
把答案写进本次提交的验证步骤里，而不是等下一轮审查。

## 八、单次通过的检查节奏（建议）

1. **改之前**：把要改的点按本清单归类（是 A 类还是 B 类？），预判会牵连哪些
2. **改的时候**：一 bug 一提交，提交信息写清「改什么 + 怎么验」
3. **改完**：过清单 → 跑 L1/L2 → 装机跑 L3
4. **报告时**：每个修复标注验证级别；L1–L3 的明确写「待实测」
5. **收尾**：把这次新踩的坑**回填到本清单**（这是清单能持续有效的唯一方式）
