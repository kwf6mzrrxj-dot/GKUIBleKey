# 实时活动（Live Activity）

锁屏卡 / 灵动岛 / CarPlay 三套画布，共用一份 `ContentState`。

> **它不只是 UI**：iOS 26 起，App 有 `CBManager` 实例并启动 Live Activity 后，
> 后台可获得与前台相同的 BLE 权限（`AllowDuplicates` 继续生效）。
> 没有它，后台广播会被系统合并成十几秒一次，预认证的 29 秒节奏必然跑不准。
> 详见 `VehicleActivityAttributes` 头注释。

## 一、三套画布

| 画布 | 由谁渲染 | 内容 |
|---|---|---|
| 锁屏 / 通知中心 | `LockScreenView`（`.small`） | 车名 + 来源 + 锁态 + 时间 + 四格 |
| CarPlay | 同一个 View（`.medium`） | 同上，字号 ×1.45 |
| 灵动岛展开 | `DynamicIslandExpandedRegion` | 车名 / 锁态+时间 / 四格 |
| 灵动岛紧凑 | `compactLeading` + `compactTrailing` | 钥匙图标 + 锁态 |
| 灵动岛最小 | `minimal` | 仅图标 |

灵动岛展开态的四格与锁屏**必须给出同一组结论** —— 长按展开后信息比锁屏更少，
会让人以为锁屏那版是错的。所以判定逻辑提取成文件级的 `StatGrid`，
两处共用，而不是各写一遍。

## 二、四格为什么是「门 / 窗 / 后箱 / 引擎」

2026-11-07 把原来的「电源」换掉了。

这张卡绝大多数时候是**站在车外**看的。那一刻：

- 「窗关没关」→ 决定要不要回去关，**原来完全没显示**
- 「电源通没通」→ ACC / 点火档只有坐在车里才有意义

`VehicleSnapshot.isWindowsClosed` 一直有值（蓝牙源时由 `snapshotFromBluetooth`
从云端补），只是从没传进卡片。这次补上了。

## 三、颜色语气：不能用一条通用规则

原来的规则是 `value == true ? 白 : 橙`。对门 / 后箱成立（关着常态、开着留意），
**但套到引擎上就反了**：停着显示橙色警示、转着显示白色。

车停着是常态，不该报警；引擎在转（远程启动中 / 车正在被使用）才值得留意。

所以改成由每个字段自己声明「哪个方向算异常」，`StatTone` 三档：

| 语气 | 颜色 | 用于 |
|---|---|---|
| `.normal` | 白 | 门关 / 窗关 / 后箱关 / 引擎停 |
| `.alert` | 橙 | 门开 / 窗开 / 天窗开 / 后箱开 / 引擎转 |
| `.unknown` | 白 35% | 没上报过，显示「—」 |

**没有一个通用规则能同时对上这四项** —— 每个字段的「异常方向」不一样。

## 四、门：能说出「哪一扇」

`doorClosed: [Bool]?`（左前/右前/左后/右后）传进卡片后：

| 情况 | 显示 |
|---|---|
| 四门全关 | 关 |
| 只有左后开 | **左后** |
| 两扇以上开 | 2门开 |
| 无逐门数据 | 退回聚合值「开 / 关」 |

「有门开着」和「左后门开着」是两个量级的信息 —— 前者要绕车检查一圈，
后者直接走过去关。

## 五、窗：车窗与天窗合并，但分开表达

| 情况 | 显示 |
|---|---|
| 车窗开 | 开 |
| 只有天窗开 | 天 |
| 都关 | 关 |
| 车窗未知、天窗没开 | — |

**天窗未知时以车窗为准显示「关」，不因为天窗不确定就报「—」。**
两条理由：没有天窗的车型该字段可能恒缺，要求"天窗已知才敢说关"会让这类车
永远显示「—」，把一个能确定的答案变成不知道；且车窗才是进水的常见来源。

## 六、时间只说一次

原来「蓝牙 · 19:28」（`statusText`）和右边的相对时间（`lastReportedAt`）
说的是同一件事 —— 最后一次收到广播。锁屏上并列两个时间，
用户得先判断哪个是哪个才能回答"这数据新不新"。

现在 `statusText` 只说来源（`StatusSource.label`：蓝牙实时 / 云端 / 暂无数据），
时间统一由 `lastReportedAt` 以相对形式表达 ——「3 分钟前」比「19:28」直接。

## 七、`staleDate` 与 `isStale`

### 为什么要设

之前传 `nil`：App 被系统杀掉后没有任何代码在更新卡片，
系统也不会把它标成过期 —— 锁屏上一直挂着一份**看起来是实时的旧状态**。
用户据此判断"车锁着"然后走开，比没有卡片更危险。

### 阈值：20 分钟（不是 5 分钟）

最初取 300 秒，理由是"比 `VehicleSnapshot.staleSeconds`（180 s）宽一档"。
那个思路错了 —— **两个阈值量的不是一回事**：

| 阈值 | 回答的问题 |
|---|---|
| `VehicleSnapshot.staleSeconds`（180 s） | 这份数据能不能用来做决策（远程控车前要确认） |
| `staleDate`（1200 s） | 这张卡片还可能代表现状吗 |

**车锁状态在没人动它时是稳定的。** 用户锁车走开、蓝牙断开、收不到广播，
这是最正常的场景；此时卡片上写「已锁」依然是对的，5 分钟就标成「过期」属于误报。

20 分钟的依据：超过这个时长，人大概率已离开车的视野，且期间车辆被他人操作的可能性
开始不可忽略 —— 那时提示"可能已过期"才有价值。

### ⚠️ 设了必须读

`staleDate` 只是给开发者的标记，**系统不会自动改变外观**。
上一版只设了它，整个 Widget 里没有一处读 `context.isStale` ——
等于白设。这是本轮审查发现的真实缺陷。

现在锁屏卡和灵动岛展开态都读：过期时把时间标成橙色并加 `exclamationmark.triangle.fill`。
克制但明确 —— 不整卡变灰（那会让正常离车场景显得像出了问题）。

### 什么时候会真的触发

`measured.$status` 每帧广播都会调 `refreshLiveActivity()`（内部 2 秒节流），
所以只要 App 活着且收得到广播，staleDate 一直被推后。
真正触发只有一种情况：**App 被系统杀掉，或长时间收不到任何车辆数据**。

## 八、验证

| 项 | 结果 |
|---|---|
| 判定矩阵（19 组边界） | ✅ 抽成纯 Swift 复现，全部通过 |
| `typecheck` | ✅ 0 error（66 文件 / 21,515 行） |
| `xcodebuild`（含 Widget target） | ✅ BUILD SUCCEEDED |
| 锁屏 / 灵动岛实际观感 | ❌ **未装机验证**（设备不可达） |

判定矩阵覆盖：四门全关 / 单门开 / 多门开 / 无逐门数据 / 窗开 / 天窗开 /
窗关天窗未知 / 各字段未知 / 引擎转与停。其中「引擎停着是白」这条
就是照着这次修的 bug 写的断言。

## 九、已知边界

1. **纯蓝牙用户看不到窗位**。蓝牙 16 字节广播里没有窗位字段，只有云端有。
   没配云端的用户，这一格永远是「—」—— 那是诚实的（不知道 ≠ 关着），
   但也意味着「窗」这一格对他们没有信息量。
2. **没显示油量**。CarPlay 画布更宽，理论上放得下，但目前 medium 只是等比放大，
   加第六项会挤掉门窗。等真的给 CarPlay 做横向布局时再考虑。
3. **位置没进卡片**。状态页有地图卡，实时活动里放坐标没有操作价值
   （点不进地图，也不该在锁屏暴露停车位置）。

### 已删除的死字段（2026-11-07）

`ContentState` 曾有四个字段没有任何消费方：

| 字段 | 处理 |
|---|---|
| `fuelLevel` | v9.9 新加但从未显示 → 删 |
| `isAccOn` / `isIgnitionOn` | v9.2 曾用于「电源」格，v9.9 换掉后零引用 → 删 |

留着的唯一理由是"将来可能用"，而那不是保留死代码的理由 ——
真要做 CarPlay 横向布局时重新接一遍数据，比现在维护三个假接口便宜。
